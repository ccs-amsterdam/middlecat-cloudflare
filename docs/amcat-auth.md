# AmCAT authentication: recommendation

## Context
AmCAT servers default to MiddleCat (a central, registration-free OIDC provider). Users will tend to stay on
MiddleCat even for sensitive data, so the default has to be as safe as possible. Question: should AmCAT do its
own auth, should MiddleCat/our hosted IdP add 2FA, or should AmCAT add its own second factor?

## Main risk
MiddleCat (or any IdP we host) is a single issuer trusted by every default AmCAT server. If it is compromised
(signing key, `KEY_ENCRYPTION_SECRET`, Cloudflare account, npm/Better Auth supply chain, email provider), the
attacker can create a valid login for any email on every server. 2FA inside the IdP (MiddleCat+2FA, or Authentik)
doesn't help here: it protects the user's account at the IdP, not the servers from the IdP. A "stateless
MiddleCat that vouches for emails" has the same problem, because the signing key is still what matters.

## Recommendation: OIDC for identity, AmCAT for sessions and the second factor
1. **Keep OIDC** as the only external interface (MiddleCat by default, any IdP for those who want one). Don't build
   email/social login into AmCAT: per-server SMTP and Google/GitHub OAuth apps would become required onboarding
   steps, which is exactly the friction MiddleCat removes. (AmCAT can have optional SMTP for invitations, see below,
   but login never depends on it.)
2. **AmCAT owns the session** (an RP/application session, separate from the IdP's session). Use the id_token once at
   login (verify `iss`, `aud`, `exp`, `nonce`, `email_verified`), then issue AmCAT's own session cookie (HttpOnly,
   Secure, SameSite, idle + absolute timeout). No refresh tokens from the IdP are needed.
   - Sessions are stored in the database and checked on every request, together with the role lookup that already
     happens. Revocation is immediate. Update `last_seen` (idle timeout) at most once a minute. If this becomes a
     performance issue, add a short cache of the combined auth+role lookup for non-sensitive requests.
   - The absolute timeout also bounds offboarding: when an institution disables an account at its IdP, the AmCAT
     session ends at the latest at the absolute timeout, and a new session needs a new IdP login.
3. **AmCAT requires a local second factor for roles the server specifies**, e.g. `require_local_factor = admin | writer | all`.
   - A MiddleCat compromise is then no longer enough: the attacker also needs the user's factor on that server.
   - Two kinds of factor, behind a small interface (`enroll`, `verify`) so the flows below don't depend on which one:
     - **Passkey (WebAuthn), recommended.** Tied to the server's own origin (fits the same-origin model), resists
       phishing, and the server only stores public keys. Python: `py_webauthn`, frontend: `@simplewebauthn/browser`.
     - **Password, as a fallback** for users who don't want or understand passkeys. The enrollment form suggests a
       random password generated by AmCAT (about 128 bits, grouped for readability) and uses `autocomplete`
       attributes so the browser or password manager saves it for this server. Where the server allows it, users can
       choose their own password instead (minimum length, hashed with argon2, rate limiting and lockout).
   - The server decides what's allowed: `allowed_factors = passkey` or `passkey, password`, and whether own passwords
     are allowed or only generated ones. The default is passkeys only. Servers with sensitive data should stay on
     passkeys only, and the security description for data stewards says which mode the server runs in.
   - Within what the server allows, the user chooses at enrollment. Enrollment only happens via an invitation link
     (see below), and adding a factor or switching to another requires the current one, so an attacker can't pick a
     weaker factor for someone else.
   - **No self-service reset**, for passwords either. A user can change their password while logged in (with the
     current one), but a lost passkey or forgotten password goes through a server admin, who issues a new invitation
     link (one button in the admin screen, sent via SMTP if configured). The enrollment screen (and the password
     screen) clearly says that, for security reasons, users can't reset a lost factor themselves and recovery is only
     possible via the server administrators. A reset email would make the mailbox enough on its own for
     MiddleCat magic-link users (the mailbox gives both the OIDC login and the reset), which is the gap the second factor
     closes. This is also the norm for second factors: e.g. GitHub doesn't reset 2FA via email alone.
   - Users can register more than one factor (a second passkey or security key, or a generated password as backup
     next to a passkey, which then acts as a recovery code), and the screens encourage it. That covers most lost-factor
     cases without an admin.
   - Later option, if admins on large servers become a bottleneck: a backup user who can start a reset for someone.
     The reset is the same as an admin reset (a new invitation link to the user's own mailbox), so it is only
     available with SMTP. Choosing a backup user requires the user's own factor. The backup user needs a second
     factor and confirms with it. Old factors stay valid until a new one is enrolled. The user is notified and the
     reset is logged. Possibly not for server admins.
   - Ask for the factor again (step-up) for: creating API keys, changing users/roles, deleting indexes, server settings.
   - Not in the first version: skipping the local factor when an organization's own IdP enforces MFA (`acr`/`amr`).
     It needs a second step-up path (re-login at the IdP with `prompt=login&max_age=0`) and `acr`/`amr` are claims
     made by the IdP itself, so it would only be acceptable for an IdP trusted as much as the server. If added later,
     make it a server-wide mode, not per user.
4. **Simplify MiddleCat** once AmCAT owns sessions: drop refresh tokens, server sessions, the session dashboard and
   revocation/end-session. What remains: login → confirmation → code → tokens, plus budgets and confirmed-servers.
   Less state, less code, smaller attack surface. Keep investing in operational hardening (hardware keys on
   Cloudflare/GitHub, pinned dependencies, few dependencies, short single-use magic links bound to the browser
   that asked for them, keep sign-in links out of email provider logs where possible).

## Invitations and enrollment
Whoever first logs in as an email address could register its second factor (trust on first use). To close that gap,
enrolling requires two things from two independent parties: a valid OIDC login for that email **and** a one-time
invitation link that did not come from the IdP.

- **Roles that require a second factor are always granted through an invitation.** This applies to server roles and
  project roles alike, whether or not the user already has a factor. The role is pending until the user opens the
  link, logs in, and confirms with their factor (enrolling one first if they don't have one yet).
  - Consistent for inviters, and the invite screen doesn't reveal whether an email has an account or a factor.
  - For a user who already has a factor, the link only accepts the invitation (confirmed with the existing factor).
    It never allows enrolling an additional or different factor.
  - Pending invitations are also shown in AmCAT after login, so an enrolled user who lost the email can still
    accept. Users without a factor need the link.
  - Roles that don't require a second factor are granted directly, as now.
- **Who sends the link.** An AmCAT server has optional SMTP, separate from MiddleCat's email:
  - With SMTP, AmCAT emails the link directly to the user and the inviter never sees it. "Resend" issues a new
    token and invalidates the old one. Recommended for servers with sensitive data.
  - Without SMTP, the inviter is shown the link once (copy and `mailto:` buttons) and told to send it only to that
    person. The inviter then holds the link, so log who issued each link and who completed it, visible to server admins.
  - Use the server's own SMTP (e.g. a university relay), not MiddleCat's email provider, so the two channels stay
    independent. SPF/DKIM for the from-domain matter for deliverability. Settings: host, port, username, password,
    from-address, STARTTLS/TLS.
  - The SMTP server can also be used for notifications.
- **Link and token.**
  - Link: `https://<server>/invite#<token>`. The fragment keeps the token out of server logs and Referer headers.
    The frontend passes it to the API, and it's kept in the pre-login session during the OIDC flow.
  - Token: only a hash is stored, single use, expires after about 7 days, revocable, tied to one email address.
  - In the callback, the OIDC email must equal the invited email. If it doesn't, show a clear message
    ("this invitation is for x@uni.nl, you are logged in as y@uni.nl").
  - Email content: plain text, with the inviter's name, the project, and the server URL. Say that the link only works
    when logged in as that address, and that unexpected emails can be ignored.
- **Same mechanism for:**
  - Promotion to a role that requires a second factor.
  - Recovery: a server admin removes the user's factors (passkeys or password) and issues a new link.
  - The first admin: a CLI command on the server, e.g. `amcat4 invite admin@uni.nl`, which prints the link or sends
    it via SMTP.
- **Guests** (access via `guest_role`, no explicit role) don't need a second factor, since nobody invites them.

## Trust model for sensitive roles
| Compromised | Effect |
|---|---|
| OIDC provider (e.g. MiddleCat) | Safe, as long as the user's mailbox and AmCAT's SMTP are secure: the attacker can't get the invitation link, and can't use an existing factor. |
| AmCAT's SMTP server | Safe: the attacker gets the link but still needs an OIDC login as the user. |
| The user's mailbox | Only a problem if the user hasn't enrolled a factor yet (MiddleCat's magic link and the invitation both arrive there), or stores their password there. Accepted risk; the enrollment screen says not to email the password to yourself. |
| Inviter, without SMTP | Needs an OIDC compromise as well, and only works for a user without a factor yet. Logged. |
| Lost passkey or password | Not a compromise: recovery is a human process via a server admin. |
| The AmCAT server itself | Out of scope: it holds the data. |

## Notes on the protocol
- AmCAT is a public OIDC client using PKCE, without a client secret, and MiddleCat uses the server's URL as
  `client_id`. That's in line with current specs (OAuth 2.1, PKCE, IndieAuth, the IETF draft "OAuth Client ID
  Metadata Document"). A secret wouldn't help against the main risk.
- Open point: without a secret, anyone can start logins attributed to a server, and logins are counted when they
  start, so a script could use up a server's budget or the free tier. Consider counting completed logins, or
  rate-limiting starts per IP.
- Session-cookie theft (infostealers) after login is not solved by any option. Device-bound cookies with a
  non-extractable WebCrypto key in IndexedDB were considered and dropped: the key is still stored in the browser
  profile, so copying the profile copies the key. Mitigate with short idle timeouts, step-up for sensitive actions,
  and API keys with expiry/scopes that can only be created with step-up.

## Rejected
- MiddleCat + 2FA: more state and responsibility, still a single point of failure for all servers.
- Hosted Authentik + CLI registration: same single point, more ops, more attack surface, and registration friction.
- AmCAT doing all auth itself: much more friction, and a central email verifier is still needed in practice.
- TOTP as a local factor: somewhat better than a password against phishing, but more work for users and to build
  (an encrypted shared secret, rate limiting, replay protection, QR enrollment). The password fallback serves the
  "I don't understand passkeys" case better.
- Self-service password reset by email: see the second factor above.
- MiddleCat sending AmCAT's emails: it would merge the two independent channels into one party.
- Project admins issuing enrollment-only links separate from role invitations: all roles that need a second factor go through the same
  invitation flow instead.

## Next steps (when implementing)
- AmCAT (`backend/amcat4/auth/`):
  - Own sessions in the database after OIDC login.
  - Local factors (WebAuthn, and the password fallback), and the `require_local_factor`/`allowed_factors` settings.
  - Invitations with pending roles, and optional SMTP.
  - Step-up on sensitive endpoints.
  - Recovery and invite CLI.
  - Audit log of logins, factor changes, invitations, step-ups, role changes and API key creation.
- MiddleCat (`src/routes`, `src/lib`): remove refresh tokens/sessions after AmCAT no longer uses them; update README/design.md.
- A one-page security description for data stewards. It covers:
  - where identity comes from;
  - the session and its timeouts;
  - the second factor for privileged roles (passkey, or which password mode is allowed);
  - step-up;
  - invitations;
  - admin-only recovery;
  - what is logged.
